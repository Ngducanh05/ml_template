# Automatic Canary traffic - explicit demo/test opt-in

This adapter reuses scripts/e2e_v2/runner.py. Release authorization, Controller phases, Router weights, Prometheus queries and security policy are unchanged. Default V2_AUTOMATIC_TRAFFIC=false: no Job API calls or traffic. Source implementation is not live acceptance.

## Opt-in and lifecycle
After separate operator approval, configure the controller with V2_AUTOMATIC_TRAFFIC=true, V2_SYNTHETIC_GATE_APPROVAL=<approved non-sensitive ticket>, V2_TRAFFIC_IMAGE=<new tested control-plane repository@sha256>. Approval covers synthetic requests contributing to the ordinary Canary quality gate; they are not independent evidence of organic production demand. An opt-in reference is an operational record, not a substitute for native per-release human approval.

After the normal controller tick, the adapter considers only an active RAMP at weight10/25/50/100 with a valid exact claimed authorization and unchanged Stable baseline. Existing KServeEffects readiness verifies both lanes before Job creation. The Job name is deterministic from authorization identity; full identity/config/code annotations detect collisions or drift. An existing Job, including failed, completed or suspended, is never recreated/retried. No state mutation is performed by the adapter or generator.

The Job uses the existing runner, fixed 2 RPS, concurrency1, at most2000requests, duration900s, Kubernetes deadline930s, backoffLimit0, one completion. These do not exceed existing runner limits. One request uses the existing small synthetic_credit_risk.json payload. Exact candidate runtime/version/artifact/fingerprint/authorization and previous Stable are checked before each submission; observedGeneration, exact Deployment images/annotations/ready replicas, both metadata signatures and payload compatibility are checked. Traffic goes only through Router-v2 and retains X-Traffic-Origin: synthetic and X-E2E-Run.

Only RAMP permits sends. The automatic observer, including a slow-start Pod, follows the same exact authorization through FINALIZING, DRAINING and ROLLBACK without submitting requests. BLOCKED returns controller_blocked. Terminal PASS requires the latest contiguous release_started/release_completed audit segment with exact authorization and pair, ordered 10/25/50/100 stages, exact Stable, idle and weight0. Rollback FAIL requires the exact start/rollback authorization, failed pair and matching controller reason, restored previous Stable, idle and weight0. Missing/truncated/conflicting audit fails closed. Manual admission/replay protection is unchanged. Identity drift, loss of readiness, API error, cancellation or deadline stops the run; request exhaustion stops sending but automatic observation continues within the same duration budget. Request errors are recorded; automatic release outcome remains the Controller terminal decision. At most one already-in-flight request may finish (existing HTTP timeout3s); Kubernetes/state changes cannot atomically revoke an HTTP request already sent. Failed checks do not change release status, thresholds or traffic weights. Existing no-traffic WAIT/deadline rollback still applies. Do not call a runner exit a successful promotion; durable Controller audit remains authoritative.

## Durable Job receipts and cancellation
No ttlSecondsAfterFinished: retain each Job while its authorization could be active, so restarts cannot reset budget. Cancellation uses operator-approved Job suspension (spec.suspend=true), which retains its name/receipt and terminates active Pods. Do not delete/unsuspend the Job during that authorization's active lifecycle. Only after terminal release, archive evidence and separately approve cleanup. Deleting an active receipt could allow recreation; Job retention is an operational invariant. Kubernetes Job delivery is not an exactly-once HTTP guarantee; backoff0 and concurrency1 bound attempts.

## Permissions and live proposal (NOT APPLIED)
Review k8s/release-v2/automatic-traffic-rbac.proposed.json: a new namespace-only Role gives the existing Controller SA get/create Jobs; a separate traffic SA only gets model-release-state-v2 and the two exact predictor Deployments. No state update, AWS identity, secrets, KServe mutation, job delete/update/list or cluster-wide RBAC. Kubernetes cannot constrain create Jobs by resourceNames: this grants namespace-scoped workload creation to the already trusted controller. Code fixes SA, namespace, command, resource limits and names; admission/runner isolation remains an operational prerequisite.

Proposed activation prerequisites: independently approved eligible model; reviewed Release/authorization Controller image including this runner, successful tests/image security scan, immutable image publication, exact Deployment CAS patch and operator-approved synthetic opt-in. Impact: at most one additional50mCPU/64Mi-request Pod per active authorization, limits500mCPU/256Mi, no node/HPA change. First deploy with automatic traffic OFF, then approve opt-in separately. No image publication or deployment is authorized by this document.

Rollback: suspend the exact traffic Job first and retain it, then guarded restore of controller image/env from captured pre-change Deployment (resourceVersion check). Verify state/ServingPair unchanged and weight owned solely by Controller. Disabling new Job creation alone does not cancel an already-running Job; suspension or runner termination is required. Do not edit state or router weights. Missing traffic may cause the existing policy timeout and exact-pair rollback, which is expected.
